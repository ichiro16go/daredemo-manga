## 前提

- 体制: PM(あなた)1人 + 複数のClaude Codeエージェントを並行稼働。holonica-studioのPM+サブエージェントモデル(`CLAUDE.md`)と同じ考え方
- 進め方: **issue-driven**。機能を独立したGitHub Issueに分解し、依存関係のないIssueは複数エージェントに同時に投げる。日別の逐次スケジュールではなく、「依存関係で束ねたwave(並列実行可能な単位)」で管理する
- スコープ: PC版 F-01〜F-08 すべて + スマホ版 SP-01/SP-02。期限は目安1ヶ月、延長許容
- PMの役割(holonicaのCLAUDE.mdに準拠): Issue分解・依存関係の整理・エージェントへの割り当て・PRレビュー・マージ判断。コードは直接書かず、実装はエージェントに委譲
- 各Issueには「担当エージェントが実装 → PMまたは別エージェントがレビュー → マージ」のサイクルを想定。品質担保のため、レビュー(code-reviewer相当)を挟むIssueには明記する

## 進め方の型

1. wave内のIssueをGitHub Issueとして作成(ラベル: `area:infra` `area:editor` `area:mobile` `area:monetize` `area:qa`)
2. 同一wave内で依存のないIssueは並列でエージェントにアサイン
3. wave完了(全IssueがマージされGREEN)を確認してから次waveに着手。ただし依存のないIssueは前倒しで次waveから先に着手してよい(下記「並列前倒し可否」参照)
4. wave境界で軽くPMレビュー(進捗確認・スコープ調整の判断ポイント)

## リスク・調整ポイント

- 並列実行は「エージェント数を増やせば時間が線形に縮む」わけではない。PMのレビュー・マージ判断がボトルネックになりやすいので、wave内で一度に走らせるエージェント数はPMがレビューし切れる範囲に抑える
- EDIT-F08-1(投稿スキーマ)は最も影響範囲が広いIssue。Wave4の中でも最優先で着手・レビューし、Wave6着手前に確定させる
- EDIT-F03-1(ポーズ差分の一貫性)とEDIT-F04-2(着彩の配色記憶)はAIプロンプト設計の試行錯誤が発生しやすく、見積りがぶれやすい最有力候補
- 1ヶ月という目安に対し、Wave0〜7の直列的な依存の深さ(基盤→機能第一段階→拡張→統合→モバイル→リリース)を考えると、並列化してもクリティカルパス自体は短縮しにくい。並列化が効くのは「同時に着手できるIssue数」であって「waveの数」ではない点に注意
